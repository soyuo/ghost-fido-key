# Virtual FIDO2 Security Key 구현 작업 계획

이 문서는 [`DUPLICATE.md`](./DUPLICATE.md)의 기존 구현 조사와 [`SPEC.md`](./SPEC.md)의 요구사항을 실행 가능한 순서로 나눈 v1 작업 계획이다. 각 단계는 앞 단계의 완료 조건을 충족한 뒤 진행한다. 구현 중 명세와 충돌하는 기술 제약이 발견되면 코드를 우회 구현하기 전에 해당 결정과 영향을 `SPEC.md`에 기록한다.

## 진행 원칙

- 대상은 Windows 11 x64 데스크톱 애플리케이션이며 물리 USB 장치 없이 가상 USB HID FIDO 인증기를 제공한다.
- 실제 USB 장치 열거, CTAPHID, CTAP2, 브라우저 WebAuthn 흐름을 각각 검증한다. UI만으로 완료를 판정하지 않는다.
- USB/IP + VHCI와 Windows UdeCx는 서로 다른 구현 경로다. 초기에 실제 대상 환경에서 실행 가능성, 드라이버 서명·설치·배포, 관리자 권한, 유지보수 및 라이선스를 비교해 v1 경로를 확정한다. 불가능한 경우에만 대체 경로를 채택하고 명세를 갱신한다.
- `DUPLICATE.md`의 프로젝트들은 참고 자료다. 코드, 프로토콜 구현, 식별자 또는 보안 주장을 검토 없이 복사하지 않는다. 출처와 라이선스를 확인한다.
- 타사 제품의 VID/PID, 제조사, AAGUID 또는 attestation을 사칭하지 않는다. 이 제품은 소프트웨어 인증기이며 물리 보안 키와 동등한 보안을 보장한다고 표시하지 않는다.
- 각 단계의 산출물과 완료 기준을 기록한다. 지원하지 않는 환경과 웹사이트는 구체적으로 문서화한다.

## 0단계: 저장소와 요구사항 기준선 확정

### 0단계 작업

- 저장소 상태, 기존 코드, 빌드 도구, 개발 환경을 조사한다.
- `SPEC.md`의 필수 목표 G-001부터 G-015까지를 요구사항 추적표로 정리하고 각 항목에 구현 모듈, 검증 방법, 담당 단계 ID를 연결한다.
- `DUPLICATE.md`에 열거된 Virtual-FIDO, softfido, passless, fidorium, HID bridge 등의 저장소·문서·라이선스를 확인한다. 조사 메모의 주장과 현재 상태가 다르면 검증된 사실로 갱신한다.
- Windows 11 x64, .NET SDK, Windows SDK, 브라우저, TPM 상태를 개발 및 최소 테스트 환경으로 정의한다.
- v1 범위와 비목표를 고정한다. 일반 USB 개조, BLE/NFC, 클라우드 동기화, macOS/Linux는 제외한다.

### 0단계 완료 기준

- 필수 목표 각각에 검증 가능한 완료 기준이 연결되어 있다.
- 외부 프로젝트의 참고 범위와 라이선스가 기록되어 있다.
- 저장소에 기존 구현이 있다면 보존 범위와 변경 기준선이 명확하다.

## 1단계: 드라이버·전송 경로 기술 검증

### 1단계 작업

- USB/IP + VHCI 후보와 Windows UdeCx 후보를 비교한다. Windows 11 호환성, 장치 열거 방식, 설치 권한, 서명 요구사항, 재부팅 필요성, 배포와 제거, 장애 복구 및 상용 배포 조건을 조사한다.
- 각 후보로 최소 실험을 수행한다. FIDO HID descriptor와 interrupt IN/OUT endpoint를 가진 테스트 장치가 Windows 장치 관리자에 열거되는지 확인한다.
- 사용자 모드 서비스와 드라이버 사이의 API, 요청 큐, 연결·분리 이벤트 및 오류 전달을 확인한다.
- 선택한 경로에서 브라우저나 Windows가 FIDO HID 장치로 검색할 수 있는지 검증한다. 단순 장치 열거와 WebAuthn 호환은 별도 결과로 남긴다.
- `USB/IP + VHCI 우선 검토, UdeCx 대안`이라는 명세의 초기 방향을 실험 결과에 따라 확정한다.

### 1단계 완료 기준

- 실제 Windows 11 x64에서 물리 USB 없이 가상 FIDO HID 장치가 연결 및 분리된다.
- 드라이버 설치·제거와 권한 요구사항이 재현 가능한 절차로 문서화되어 있다.
- v1 전송 구현 경로와 대안 전환 조건이 `SPEC.md`에 확정되어 있다.
- 적합한 경로가 없으면 구현을 진행하지 않고 제한 사항과 가능한 제품 범위 변경을 기록한다.

## 2단계: 솔루션 골격과 모듈 경계 구성

### 2단계 작업

- `SPEC.md`의 권장 구조를 기준으로 솔루션과 프로젝트를 만든다: Desktop, Service, Transport, Ctap, Authenticator, Security, Storage, Contracts.
- 프로젝트 참조 방향을 단방향으로 정하고 공용 인터페이스와 DTO를 Contracts에 둔다.
- USB 전송은 인증 엔진에서 추상화하여 USB/IP와 UdeCx 구현을 교체할 수 있게 한다.
- nullable, 경고, 분석기, 포맷, 빌드 구성(Debug/Release), 버전 관리 및 의존성 정책을 설정한다.
- 운영체제 기능, 드라이버 통신, 데이터베이스, UI의 경계를 정의하고 각 모듈의 책임을 문서화한다.
- 진단 로그의 비밀정보 제외 정책과 오류 코드 매핑을 마련한다.

### 2단계 완료 기준

- 전체 솔루션이 빌드되고 각 프로젝트가 의도한 참조만 가진다.
- USB 구현을 바꾸어도 CTAP 및 인증기 계층의 public 계약을 바꾸지 않아도 되는 구조다.
- 비밀값을 로그에 기록하지 않는 로깅 공통 규칙이 적용되어 있다.

## 3단계: 가상 USB HID 장치와 수명주기

### 3단계 작업

- FIDO HID descriptor를 구현한다. FIDO Usage Page `0xF1D0`, CTAPHID Usage `0x01`, interrupt IN/OUT, 보고서 크기 등은 명세와 공식 규격에 대조한다.
- 가상 장치 생성, 연결, 상태 확인, 분리 및 실패 시 롤백을 구현한다.
- 장치 연결 요청 전 세션, 서비스 상태, 저장소 접근성, 드라이버 가용성을 점검한다.
- 정상 종료, 서비스 중지, 사용자 로그오프, 강제 종료 후 재실행 시 잔류 장치 정리와 복구를 구현한다.
- 가상 장치 상태를 서비스와 UI에 전달한다. 연결됨 표시는 실제 OS 장치 열거 확인 후에만 설정한다.
- 드라이버 및 장치 식별 정책을 구현한다. 타사 제조사 식별자를 사용하지 않는다.

### 3단계 완료 기준

- 물리 USB 없이 Windows 장치 관리자와 HID 열거에서 장치를 확인할 수 있다.
- 반복 연결·분리, 앱 정상 종료, 서비스 재시작 후 장치 상태가 일관된다.
- 각 실패 경로에서 장치 또는 핸들이 유실되지 않고 오류 코드와 사용자 안내가 제공된다.

## 4단계: CTAPHID 전송 구현

### 4단계 작업

- 64바이트 HID report 처리와 초기·후속 프레임 분할 및 재조립을 구현한다.
- 채널 할당, 채널별 상태, 잘못된 채널 처리, 동시 요청 및 타임아웃을 구현한다.
- 우선 `INIT`, `PING`, `CBOR`, `CANCEL`, `KEEPALIVE`, `ERROR`를 구현한다.
- 최대 메시지 길이, 잘못된 sequence, 잘린 프레임, 초과 데이터, 취소 및 시간 초과 처리를 명세에 맞춘다.
- 전송 계층과 CTAP 명령 처리 사이에 바이트 스트림 대신 명확한 메시지 계약을 둔다.
- 프로토콜 오류를 표준 CTAPHID 오류 응답으로 변환하고 상세 내부 오류는 안전한 진단 로그로 남긴다.

### 4단계 완료 기준

- CTAPHID 테스트 도구 또는 자체 검증 클라이언트로 INIT, PING, CBOR 왕복이 동작한다.
- 분할·재조립, 채널 격리, CANCEL, KEEPALIVE, 오류 및 시간 초과 동작이 검증된다.
- 비정상 입력으로 서비스가 종료되거나 다른 채널의 상태가 오염되지 않는다.

## 5단계: CBOR 및 CTAP2 기본 명령

### 5단계 작업

- 지원할 CTAP 버전과 기능을 확정하고 `GetInfo`의 버전, 옵션, 최대 메시지 크기, 알고리즘 및 AAGUID 정책을 명세한다.
- CBOR 인코더·디코더를 선택하거나 구현한다. 중복 키, 비정규 입력, 예상 밖 타입, 과도한 중첩·크기 및 잘린 데이터의 거부 동작을 정한다.
- 표준 CBOR map 키, 바이트 문자열, 정수, null 및 응답 인코딩을 처리한다.
- `GetInfo`부터 구현하고 `MakeCredential`, `GetAssertion`, `ClientPIN`, `Reset` 및 필요한 credential management 명령을 단계적으로 추가한다.
- 미지원 명령, 옵션, 확장 및 알고리즘에 대해 규격에 맞는 오류를 돌려준다.
- CTAP 상태 코드와 내부 오류 코드를 분리하고 민감한 세부정보를 외부 응답에 포함하지 않는다.

### 5단계 완료 기준

- 지원 기능이 `GetInfo`와 실제 처리 동작에서 일치한다.
- 유효한 요청과 오류 입력에 대한 CBOR 인코딩 및 CTAP 응답이 규격에 맞는다.
- 명세에 없는 기능을 지원한다고 광고하지 않는다.

## 6단계: 암호 연산과 자격 증명 데이터 모델

### 6단계 작업

- 지원 알고리즘을 우선 ES256으로 한정하고 키 생성, 공개키 인코딩, 서명 및 검증 흐름을 구현한다.
- RP ID hash, client data hash, authenticator data, flags, signature counter 및 attested credential data를 규격에 맞게 구성한다.
- 자격 증명 모델을 설계한다. credential ID, RP 정보, 사용자 핸들, 공개키, 키 참조, 생성 시각, 사용 시각과 선택 필드를 분리한다.
- discoverable credential과 allow list 기반 인증의 저장 및 조회 경로를 구현한다.
- 중복 credential, 자격 증명 개수 제한, 삭제, reset, 데이터베이스 마이그레이션을 정의한다.
- attestation은 자체 소프트웨어 인증기 신원을 정확히 표현하는 정책을 정하고, 타사 신원을 위장하지 않는다.

### 6단계 완료 기준

- 테스트 키로 credential 생성 및 서명 결과를 검증할 수 있다.
- 다른 RP의 credential이 선택되거나 인증되지 않도록 RP ID 경계가 검증된다.
- credential 저장·조회·삭제와 데이터베이스 재시작 후 일관성이 확인된다.

## 7단계: TPM/CNG 키 보호와 저장소 보안

### 7단계 작업

- Windows CNG 및 TPM 2.0에서 비추출 키를 생성하고 서명하는 경로를 구현한다.
- 키 컨테이너 식별자와 credential 메타데이터를 안전하게 연결한다. 개인 키 원문을 SQLite나 파일에 기록하지 않는다.
- SQLite에 저장되는 민감 메타데이터의 보호, 데이터베이스 ACL, 무결성, 트랜잭션, 백업 및 마이그레이션 정책을 적용한다.
- TPM 사용 가능·불가·오류 상태를 판별한다. TPM이 없을 때의 소프트웨어 키 대체 정책은 기본 비활성 또는 명시적 사용자 동의 등 보안 기준을 문서화한 뒤 구현한다.
- PIN 설정, 검증, 해시·키 파생 정책, 실패 횟수, 재시도 지연 및 잠금 정책을 구현한다. PIN 원문은 저장하지 않는다.
- 키 접근 및 복구 정책, 인증기 초기화 시 키 삭제 순서, 키 삭제 실패 처리를 구현한다.
- 키가 메모리에 머무는 시간과 폐기, 예외·크래시 덤프·로그 노출 방지 정책을 적용한다.

### 7단계 완료 기준

- 지원 환경에서 개인 키를 내보내지 않고 TPM 내 서명이 성공한다.
- TPM 미지원 및 키 접근 실패 시 UI와 프로토콜이 정의된 보안 정책을 따른다.
- 데이터베이스와 로그에 개인 키, PIN 원문 또는 인증 비밀값이 노출되지 않는다.
- 초기화와 삭제 결과가 재실행 후에도 확인된다.

## 8단계: 사용자 존재·사용자 확인·승인 흐름

### 8단계 작업

- 인증 요청마다 RP 이름/ID, 사용자 계정 식별 정보, 요청 종류 및 허용된 credential을 사용자에게 표시한다.
- 명시적 승인·거부·시간 초과·취소를 구현하고 요청 상태를 CTAP 처리와 연동한다.
- PIN 검증과 사용자 확인(User Verification), 사용자 존재(User Presence)를 서로 다른 요구사항으로 처리한다.
- 승인 UI를 위조하거나 다른 프로세스가 승인 이벤트를 주입하지 못하도록 IPC와 창 소유권을 보호한다.
- 승인 대기 중 앱 잠금, 로그오프, 연결 해제, 요청 취소가 발생하면 서명을 중단한다.
- 자동 승인이나 사용자가 인지하지 못하는 서명 경로가 없도록 상태 전이를 검토한다.

### 8단계 완료 기준

- 승인된 요청만 서명하며 거부·취소·시간 초과는 자격 증명 서명 없이 종료된다.
- 사용자가 어떤 서비스의 어떤 동작을 승인하는지 이해할 수 있다.
- 동시 요청과 취소 상황에서 승인 응답이 다른 요청에 적용되지 않는다.

## 9단계: 서비스, IPC, 저장소 및 오류 복구

### 9단계 작업

- UI 프로세스와 권한이 필요한 서비스의 책임을 나누고 서비스 시작·중지·재시작 동작을 정의한다.
- IPC에 사용자·세션 권한 확인, 메시지 스키마 검증, 요청 상관관계 ID, 크기 제한 및 재전송 방지를 적용한다.
- 프로세스 간 자격 증명 및 PIN 전달을 최소화하고 비밀값을 커맨드라인·환경 변수·로그에 싣지 않는다.
- SQLite 트랜잭션과 동시 접근 정책을 적용한다. credential 생성 도중 실패하면 부분 등록이 남지 않게 한다.
- 오류 범주(DRIVER, TRANSPORT, CTAP, SECURITY, STORAGE, IPC, APPLICATION)를 정의하고 사용자 메시지와 진단 정보를 분리한다.
- 비정상 종료 후 장치 분리, 잠금 복구, 손상 데이터 탐지, 필요한 복구 안내를 구현한다.
- 감사 로그에는 시각, 결과, 오류 범주 등 필요한 최소 정보만 기록하고 RP 데이터와 비밀값 처리 정책을 정한다.

### 9단계 완료 기준

- 권한 없는 프로세스의 IPC 접근이 거부된다.
- 장애 후 재시작해도 데이터 무결성과 장치 분리 상태가 유지된다.
- 로그만으로 운영 오류를 진단할 수 있지만 인증 비밀과 불필요한 사용자 정보는 노출되지 않는다.

## 10단계: 데스크톱 UI와 사용 흐름

### 10단계 작업

- 메인 화면에 가상 키 연결 상태, TPM 상태, 서비스 상태 및 오류 조치를 표시한다.
- 연결·분리, 잠금·잠금 해제, 설정, credential 목록과 삭제, 인증기 초기화 기능을 제공한다.
- 등록 및 인증 승인 창에 RP 정보, 작업 종류, 계정 정보와 명확한 승인·거부 동작을 표시한다.
- PIN 설정 및 변경, PIN 잠금 상태, TPM 미지원 안내 및 복구 안내를 제공한다.
- 첫 실행 시 권한과 드라이버 설치 과정을 안내하고 프로그램 종료 전에 장치 분리 결과를 표시한다.
- 화면 읽기, 키보드 조작, 고 DPI, 긴 RP 이름 및 오류 상태를 점검한다.
- 하드웨어 키 수준의 보안 인증을 받은 것처럼 오해하게 하는 문구를 제거한다.

### 10단계 완료 기준

- 주요 기능을 명령줄 조작 없이 UI에서 수행할 수 있다.
- 앱 상태와 OS 실제 장치 상태가 일치하고 승인·거부 동작이 분명하다.
- 오류와 보안 제한을 사용자가 이해할 수 있는 문구로 안내한다.

## 11단계: 브라우저 WebAuthn 상호운용

### 11단계 작업

- Windows의 장치 열거, 브라우저의 FIDO authenticator 발견, CTAPHID 통신, CTAP 명령 처리, RP 응답 수락을 각각 관찰하는 테스트 환경을 준비한다.
- Chrome과 Edge의 지원 버전, 설정, 도메인 조건, 보안 키 선택 UI 및 사용자 확인 동작을 기록한다.
- 자체 WebAuthn 테스트 RP에서 credential 등록과 인증을 수행한다. 서버는 clientDataJSON, authenticatorData, 서명을 검증하도록 구성한다.
- discoverable credential, allow list, PIN/UV 필요 요청, 거부, 취소, timeout, 중복 등록과 삭제 흐름을 검증한다.
- 주요 서비스의 보안 정책 차이를 기록한다. 특정 attestation, 하드웨어 키, 인증된 모델 또는 플랫폼 정책을 요구하는 사이트는 별도 결과로 남긴다.
- 실패 시 어느 계층(장치, 브라우저, CTAPHID, CTAP, 서명, RP 정책)에서 실패했는지 진단 가능한 증거를 수집한다.

### 11단계 완료 기준

- 최소 Chrome 및 Edge의 명시된 테스트 버전에서 테스트 RP 등록과 인증이 성공한다.
- 등록한 credential로 다시 인증할 수 있으며 서버 측 서명 검증이 성공한다.
- 호환되지 않는 서비스와 미지원 조건을 사용자 문서에 명확히 적는다.

## 12단계: 품질·보안·호환성 검증

### 12단계 작업

- `SPEC.md` 21장의 T-001부터 T-022까지를 자동화 가능한 검증과 수동 검증으로 나눠 추적한다.
- CTAPHID 프레임과 CBOR의 잘못된 입력, 길이 초과, 순서 오류, replay, 취소 및 타임아웃을 검증한다.
- 드라이버 설치 실패, 연결·분리 반복, 서비스 강제 종료, DB 손상, TPM 오류, PIN 반복 실패 및 동시 요청 복구를 검증한다.
- RP 경계, 사용자 승인 우회, 키 내보내기, IPC 접근 통제, 로그·크래시 덤프 민감정보 노출을 점검한다.
- 요구된 테스트 환경에서 Debug/Release 빌드, 정적 분석 및 프로토콜 상호운용 검증을 수행한다.
- 발견된 결함을 우선순위와 재현 절차가 포함된 이슈로 기록하고, 차단 결함을 해결한 뒤 회귀 검증한다.

### 12단계 완료 기준

- 필수 인수 테스트가 모두 통과하거나, 미통과 항목이 출시 차단 여부와 함께 승인된 예외로 기록되어 있다.
- 보안 핵심 테스트에서 미해결 고위험 결함이 없다.
- 지원 플랫폼·브라우저·TPM 조건과 알려진 제한이 검증 증거와 함께 문서화되어 있다.

## 13단계: 설치·업데이트·제거 및 배포 준비

### 13단계 작업

- 앱, 서비스, 드라이버의 설치·업데이트·제거 순서와 권한 요구를 정의한다.
- 드라이버 패키지 서명과 앱 코드 서명, 설치 무결성, 버전 호환성 및 롤백 절차를 마련한다.
- 업데이트·제거 시 가상 장치 분리, 서비스 종료, 데이터 유지 또는 삭제 선택, TPM 키와 credential의 처리 정책을 구현한다.
- 설치 실패·업데이트 중단·롤백·재부팅 후 복구를 검증한다.
- 사용 설명서, 개인정보 및 로그 정책, 보안 한계, 지원 환경, 장애 수집 절차를 작성한다.
- 제3자 의존성, 라이선스 고지, 드라이버 배포 권한과 출처 표기를 확인한다.

### 13단계 완료 기준

- 깨끗한 Windows 11 x64 환경에 설치해 사용할 수 있고 제거 후 드라이버와 장치가 잔류하지 않는다.
- 앱 및 드라이버 서명 상태가 설치 과정에서 확인된다.
- 사용자의 credential 보존·삭제 선택이 명확하고 실제 결과와 일치한다.

## 14단계: v1 릴리스 및 완료 판정

### 14단계 작업

- 요구사항 추적표의 G-001부터 G-015까지 각 증거를 최종 검토한다.
- `SPEC.md` 26장의 v1 완료 정의 15개 항목을 인수 체크리스트로 사용한다.
- 알려진 제한, 호환성 매트릭스, 보안 설명, 드라이버 설치 조건 및 복구 절차를 배포 문서에 반영한다.
- 설치 패키지와 코드·드라이버 서명, 버전, 해시 및 릴리스 노트를 검토한다.
- 재현 가능한 최종 테스트 환경에서 설치부터 등록, 재인증, 승인 거부, 정상 종료, 강제 종료 복구, 제거까지 릴리스 검증을 수행한다.

### 14단계 완료 기준

- 물리 USB 없이 설치 및 실행되고 Windows에서 가상 FIDO USB HID로 열거된다.
- CTAPHID와 필수 CTAP2 명령, 보안 키 등록 및 재인증이 지원 환경에서 동작한다.
- 요청별 사용자 승인, PIN 정책, TPM 키 보호 정책, 안전한 연결 해제 및 복구가 동작한다.
- 인수 테스트와 배포 검증 증거가 보관되고, 미지원 웹사이트 및 보안 한계가 공개되어 있다.
- 완료 조건을 충족하지 못하면 v1 완료로 표시하지 않고 남은 차단 작업을 명시한다.
